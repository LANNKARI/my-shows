# EpisyHub Android 0.2.0: быстрые отметки и социальные функции

## Отметки серий

В 0.1.0 каждое сохранение ожидало POST quick-progress, затем заново загружало всю библиотеку GET user-shows. Кнопка блокировалась до завершения обоих запросов.

В 0.2.0 предварительный прогресс следующей серии отображается сразу с подписью «Сохраняем отметку…». Серверная ревизия и статус до подтверждения не подменяются. Успешный ответ уже содержит progress/status/updatedAt: они применяются локально, без второго GET всей библиотеки. Undo использует прежний серверный токен и тоже обходится без повторной загрузки при успехе.

При ошибке предварительное изменение откатывается и выполняется сверка с сервером. Это важно при потерянном ответе: POST мог завершиться успешно, поэтому приложение не повторяет мутацию автоматически. Если сверка невозможна из-за сети, следующая отметка блокируется до успешного обновления. Защита от устаревшей ревизии (409) сохраняется. Завершённый фильм отображает просмотр 1/1 даже если сервер только что создал для него служебную запись эпизода.

## Новые экраны

- Собственный и публичный профиль: имя, описание, статистика, любимые истории и достижения.
- Редактирование имени и описания; аватары отображаются из сайта, загрузка новых аватаров пока остаётся на сайте.
- Друзья, поиск по имени / нику, входящие и исходящие заявки, добавление, принятие, отклонение и отмена. Удаление из друзей требует подтверждения.
- Внутренняя лента уведомлений: новые серии и заявки в друзья, фильтр непрочитанных, пагинация, отдельное / массовое прочтение, настройки подписок.
- Массовое прочтение отправляет throughId и throughFriendId из загруженного снимка: более новые заявки не становятся прочитанными случайно.

Все функции используют существующие API и bearer-сессию. Изменений серверного кода, схемы базы и развёртывания сайта для этой версии не требуется. Push при закрытом приложении в эту версию не входит.

## Проверка

Расширен `mobile/tests/e2e.cjs`: реальный React Native Web интерфейс → существующий Next.js API → отдельная временная схема локальной PostgreSQL. HTTP-мост воспроизводит нативные запросы без CORS и не подменяет данные API.

Проверяются предварительный прогресс до пропуска задержанного запроса, отсутствие GET всей библиотеки после успешной отметки и undo, откат при отсутствии сети, потеря ответа уже сохранённой операции без автоматического повтора, восстановление после 409, фильм без исходного списка серий, редактирование профиля, поиск / добавление / отмена / принятие / удаление друзей, пагинация уведомлений, чтение, настройки и защита новых заявок от массового прочтения старого снимка.

SecureStore и поведение обновлённого APK на физическом Android проверяются установкой тестовой сборки на устройство.

Результат проверки 2026-11-09: TypeScript и ESLint мобильного проекта прошли; Expo Doctor — 20/20. Полный браузерный сценарий прошёл, включая одновременное обновление ленты во время задержанного массового прочтения: новая заявка остаётся непрочитанной как в PostgreSQL, так и в UI. Необработанных ошибок браузера нет.

Дополнительные проверки: переключение фильтра уведомлений во время задержанного массового прочтения не оставляет ленту в загрузке; refresh использует актуальный путь ресурса. Поздний 401 от ресурса уже закрытой сессии не завершает новый вход. Оба сценария проверены в полном браузерном прогоне с реальной локальной PostgreSQL.

## Android 0.2.1: загрузка и отдельные серии

- Библиотека используется совместно главной, поиском, календарём и карточкой, а социальные GET-ответы — соответствующими экранами. Данные хранятся только в памяти одного входа, максимум 60 ответов. При повторном переходе в течение 30 секунд свежий ответ используется без сети; устаревшие данные остаются видимыми во время обновления. Одинаковые параллельные GET объединяются. Ручное обновление и возвращение из фона запрашивают актуальные данные.
- Изменения сбрасывают свежесть связанных ответов, в том числе статистики профиля и календаря. Версии запросов защищают кэш от старого GET, пришедшего после сохранения. Кэш заново создаётся при новом входе, включая вход другого пользователя.
- При восстановлении сохранённого входа нет отдельного блокирующего GET `/api/mobile/session`: защищённые запросы данных сами проверяют bearer-сессию и обрабатывают 401. Срок действия сохранённой сессии проверяется локально до открытия экранов.
- Каждая строка серии теперь переключает именно эту серию существующим POST `/api/user-shows/{showId}` с `{episodeId, watched}`. Адрес содержит Show.id, а не UserShow.id. Старый PATCH episodes использовать нельзя: он адресует EpisodeProgress.id. Ответ применяется без полной перезагрузки. Снятие отметки работает и после выхода из карточки / истечения quick-undo, включая завершённый сериал: сервер возвращает статус «Смотрю».
- Предварительная отметка отображается до ответа. Повторные записи блокируются на уровне общей сессии, в том числе при навигации во время сохранения. Ошибка откатывает предварительное изменение и требует сверки с сервером; потерянные ответы не вызывают автоматического повторения записи.
- Длинный список серий использует FlatList; проверка отметок — Set, расчёты прогресса повторно используются для неизменённых записей. Маленькие TMDB-постеры в списках запрашиваются в размере w185 вместо w500; обложки и загруженные пользователями изображения сохраняют свои адреса.

Проверка включает семь тестов кэша и полный сценарий React Native Web → Next.js → изолированная PostgreSQL: навигация с одним GET библиотеки, отметка второй серии раньше первой, мгновенный предварительный чекбокс при задержанной сети, завершение сериала, повторное открытие и снятие отметки, откат без сети, а также прежние сценарии quick-progress и социальных экранов. Это не замер миллисекунд на физическом телефоне; первая загрузка после запуска по-прежнему зависит от API и сети.

## Android 0.2.2: очередь сохранений и серверные обращения

Запись с телефона показала приблизительно 3 секунды подтверждения отметки и 1,5–2 секунды снятия при заблокированном списке. Наблюдаемое время включает сеть и сервер; причину каждой миллисекунды по видео установить нельзя. В доступных production runtime-логах успешные операции не содержали пошаговых таймингов.

Диагностика `tests/progress-benchmark.mts` выполняет реальный `saveProgress` в отдельной временной схеме локальной PostgreSQL с Prisma query events. Для существующей записи сериала из 8 серий:

| Операция | SQL-команд до | После |
| --- | ---: | ---: |
| Первая отметка | 36 | 24 |
| Снятие отметки | 24 | 14 |
| Повторная отметка | 33 | 22 |

Счёт включает BEGIN/SET/COMMIT; проверка HTTP-сессии в этот отдельный benchmark не входит. Локальные миллисекунды не являются прогнозом времени на телефоне. Удалены no-op upsert существующей записи, повторная загрузка каталога для подсчёта уже известного изменения и лишние UPDATE. Quick-progress / undo читают после записи только прогресс, а не заново запись, тайтл и все серии. Транзакции, блокировки владельца, ревизии, даты просмотра, статистика и начисления сохранены; схема БД не меняется.

Успешные POST обеих разновидностей возвращают `Server-Timing` с auth/mutation/total. Операции от 1000 мс пишут в журнал только имя операции и длительности, без токенов и личных данных. Это позволяет сравнить реальное серверное время с ожиданием на устройстве; cold start до входа в обработчик в эти длительности не включён.

На телефоне очередь принадлежит сессии, а не карточке. Можно нажать следующую серию, выбрать другую или отменить ещё сохраняющуюся отметку сразу. Для одного тайтла сетевые записи идут последовательно, а галочки отражают последние намерения пользователя. Ответ предыдущей записи не затирает ещё ожидающие изменения. Быстрые отметки сохраняют проверку серверной ревизии и undo; разные тайтлы имеют независимые очереди. Повторные одинаковые состояния объединяются. Ошибка останавливает ожидающие записи, откатывает неподтверждённые изменения и сверяет сервер; потерянная запись автоматически не повторяется.

Проверены 110 серверных сценариев, 13 тестов кэша/очереди и полный сценарий UI → API → PostgreSQL, включая взаимодействия до ответа сервера и навигацию во время сохранения. Первый полный прогон остановился из-за исчерпания памяти dev-сервером; повторный прогон с webpack и ограничением Node heap завершился 110/110. Проверка на физическом телефоне остаётся необходимой после установки APK.

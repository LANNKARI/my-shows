# Продолжение просмотра, заметки, импорт и экономика попкорна

Согласованные макеты реализуются тремя зависимыми изменениями: добавочные модели, функции библиотеки, затем новая экономика. Ни рабочая база, ни переменные Vercel автоматически не меняются.

## Что изменилось

На главной для вошедшего пользователя — до 6 тайтлов «Смотрю». Сначала тайтлы с сохранённым временем, затем по последнему изменению прогресса. Кандидаты выбираются в PostgreSQL до загрузки эпизодов, чтобы не выгружать всю библиотеку на главную. Заметки и обычные правки метаданных не перемещают тайтл наверх. Открытие трекера не отмечает просмотр; завершённые и брошенные тайтлы исключены. При отсутствии следующей серии показывается ожидание новых серий.

В трекере есть личная заметка до 2000 символов. Она сохраняется отдельно от прогресса, не публикуется в профиле или комментариях, не приносит валюту. Есть явные состояния загрузки/сохранения/ошибки, черновик при ошибке и предупреждение перед закрытием страницы и переходом по ссылке с несохранённым текстом. В библиотеке отображается индикатор наличия заметки. Используйте «Сохранить заметку» перед навигацией браузерной кнопкой «Назад» — блокирование внутреннего history-перехода Next.js не гарантируется.

Экспорт версии 2 включает статус, заметку, личную оценку, оценки эпизодов с координатами сезон/номер, полный известный список эпизодов, прогресс, сохранённое время, настройки и коллекции.

Импорт: JSON → серверная проверка → предпросмотр → явное подтверждение → пакеты по 5 тайтлов → отчёт. Максимум 500 тайтлов, 20 000 эпизодов, 50 коллекций; серверный запрос до 2 МиБ, файл в интерфейсе до 1,9 МиБ. Существующие тайтлы и их данные не перезаписываются. Повторный запрос с прежним курсором возвращает результат обработанного пакета и не запускает следующий. После обрыва повторите «Продолжить импорт»; после перезагрузки выберите тот же файл и те же параметры, чтобы найти существующее задание. Срок предпросмотра — 24 часа с последнего открытия. Уже добавленные пакеты сохраняются при остановке.

Тайтлы сопоставляются по типу и TMDB ID, эпизоды — по сезону/номеру. Новые внешние карточки и недостающие эпизоды проверяются по TMDB до транзакции записи, до трёх запросов параллельно. Общие названия, постеры и число допустимых серий не берутся на веру из файла. Существующие названия/даты эпизодов не перезаписываются, для новых эпизодов календарные данные позже заполняет синхронизация. Если источник недоступен, пакет не записывается и доступен повтор. Неизвестные координаты и неподтверждённые дополнения к чужим локальным карточкам попадают в отчёт о пропуске. Локальные ID из файла не используются как доверенные ссылки. Для карточки без TMDB ID пользователь явно выбирает совпадение по названию/типу либо создание новой, если совпадений нет; неоднозначные и ошибочные записи пропускаются с отчётом. После изменения сопоставлений нужно повторно проверить файл.

У старого экспорта v1 отсутствуют статусы (кроме флага завершения), заметки и переносимые оценки отдельных эпизодов. В предпросмотре показывается предупреждение; пользователь явно выбирает статус для записей без него или пропускает их. Пропущенные оценки эпизодов из v1 невозможно надёжно сопоставить только по локальному episodeId. Точное восстановление отсутствующих данных не обещается.

Коллекции объединяются по единственному точному имени, элементы не дублируются. Если несколько собственных коллекций имеют одно имя, коллекция пропускается с отчётом. Импорт не восстанавливает профиль, друзей, публичные комментарии, попкорн или покупки. Просмотры и оценки из файла получают нулевые защитные записи, чтобы дальнейшее редактирование не приносило ретроспективные награды.

## Попкорн

| Источник | Награда / лимит |
| --- | --- |
| Новый пользователь | 100 один раз |
| Первый просмотр серии | 3 |
| Первый просмотр фильма | 10 |
| Первая личная оценка тайтла | 2 |
| Первый публичный отзыв от 100 Unicode-символов | 10 |
| Обычная активность | максимум 60 в сутки |
| Ежедневная серия | прежние 10 / 15 / 20 / 25 / 30 / 40 / 50 |
| Викторина по кадру | 5 за ответ, бонусы 10 за 3 подряд и 20 за 5 подряд |
| Больше или меньше | 3 в банк за ответ, бонус 5 на 3-м и 10 на 5-м раунде, полная серия 30 |
| Обе игры вместе | максимум 50 выплат в сутки |
| Два просмотренных эпизода / три оценки / два игровых раунда | задания 10 / 15 / 20 |
| Получены все 3 награды за задания | ещё 10 |

Ежедневный бонус и задания не входят в лимит активности 60. Итого без разовых наград — до 215 в день. Существующие балансы, предметы и цены косметики сохранены. Порог 10 правильных ответов пока не вводился: игра «Больше или меньше» имеет 5 раундов, а денежный бонус за 10 ответов конфликтовал бы с игровым лимитом 50. Рефералы, XP, партнёрские промокоды, сундуки, платная валюта и новые предметы не входят в этот выпуск.

В викторине ответ и варианты принадлежат серверному раунду, клиент передаёт roundId и выбранный вариант. Повтор ответа не начисляет валюту снова. Раунд действует 10 минут; максимум 120 новых раундов в час на пользователя. После денежного лимита викторина продолжает работать без валюты. В «Больше или меньше» остаются 5 дневных попыток и одна выплата банка за день; после серии или проигрыша доступна отдельная тренировка без выплат, её состояние также хранится на сервере. Если общий игровой лимит почти исчерпан, интерфейс показывает фактически выплаченную сумму, а не полный банк.

Сутки едины: 00:00 UTC (05:00 Екатеринбург). В наградах отображается время обновления в часовом поясе браузера. Задания рассчитываются по новым серверным событиям и получаются отдельными кнопками. Валютные операции атомарны и сериализуются по кошельку пользователя; постоянные ключи событий переживают удаление записи библиотеки, комментария и повторные оценки. При снятии отметки или отмене просмотра уже выданная первая награда не отзывается; повторное действие не выдаёт её снова. Проверяется факт отметки просмотра, а не реальное воспроизведение видео.

Журнал хранит причину, дату и сумму, история листается по 20 записей. Старые балансы входят как начальная запись без начисления. Изменения баланса от старой версии во время перехода фиксируются при следующей операции отдельной записью сверки; реальный баланс при сверке не меняется. Исторические события до миграции защищаются нулевыми записями и не считаются заданиями дня. Все четыре новые таблицы закрыты RLS без публичных политик; доступ осуществляется через сервер и владельца сессии.

## Порядок выкладки — важно

1. Сделайте резервную копию Supabase (структура и данные `public`, процесс Finished, файл существует). Новый экспорт сайта полезен для личной библиотеки, но не заменяет полный бэкап PostgreSQL.
2. В SQL Editor **того же проекта Supabase, на который указывает DATABASE_URL Production**, примените целиком по одному и в указанном порядке:
   - `prisma/migrations/20261027010000_personal_notes/migration.sql`
   - `prisma/migrations/20261027020000_library_import/migration.sql`
   - `prisma/migrations/20261027030000_popcorn_economy/migration.sql`
3. Каждый файл включает BEGIN/COMMIT и запускается один раз. При ошибке сохраните текст ошибки; не запускайте отдельные фрагменты повторно. Эти миграции не удаляют пользователей, прогресс, покупки и не изменяют баланс.
4. Проверьте таблицы и RLS:

```sql
SELECT c.relname, c.relrowsecurity
FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'public'
  AND c.relname IN ('PersonalNote','LibraryImportJob','PopcornEntry','PopcornQuizRound');
```

Должны быть четыре строки со значением true. До появления новых операций можно проверить, что начальные записи описывают текущий баланс; пока работает старая версия, допустимы изменения кошелька между SQL и проверкой — они сверяются при следующей операции новой версии.

5. Проверьте Preview. Вход, прежний баланс и сохранения, заметка и её приватность, продолжение просмотра, экспорт нового JSON. Для импорта используйте отдельный тестовый аккаунт и сначала смотрите предпросмотр. Проверьте повторный импорт и восстановление после остановки.
6. Объединяйте зависимые PR последовательно: сначала модели/миграции, затем библиотека/импорт, затем экономика. Дождитесь Ready / Production после каждого. Базовая ветка следующего PR должна содержать предыдущий.
7. Проверьте рабочий сайт. Новые переменные окружения не требуются. Существующий TMDB API key нужен для кадров и новых игровых пар; при недоступности источника игра показывает ошибку без начислений.

Если используете Prisma Migrate и применили SQL вручную, отдельно отметьте три миграции применёнными через `prisma migrate resolve --applied <имя_каталога>` с корректным прямым/сессионным подключением. Не используйте migrate reset или db push с потерей данных на рабочей базе.

## Проверка

API проверяются настоящей авторизацией и изолированной локальной PostgreSQL: миграции и сохранность данных, RLS, приватность заметок, read-only главная, перенос оценок/эпизодов, повторный и пакетный импорт, старый формат, welcome-награда, лимиты и повторы заданий, закрытые игровые ответы, конкуренция двух игр, сверка баланса и тренировочные раунды. Браузерные проверки Chromium используют API-фикстуры и охватывают мобильные/широкие экраны, ошибки, отмену и повтор. Production и реальные пользовательские данные автоматически не проверялись.

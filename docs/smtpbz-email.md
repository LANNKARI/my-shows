# Отправка подтверждений через SMTP.bz

Используется HTTPS API `https://api.smtp.bz/v1/smtp/send`, не SMTP-порт и не PHP. Согласно документации, ключ передаётся в Authorization без Bearer, а HTTP 200 означает успешную отправку; тело успешного ответа в Swagger не задано. Код не требует выдуманного поля success, но отклоняет явно отрицательные JSON-ответы и все HTTP-статусы кроме 200. После принятия API доставку нужно проверить в журнале SMTP.bz и ящике получателя.

Источники: https://docs.smtp.bz/#/api и https://docs.smtp.bz/ui/ (спецификация Swagger). JSON-запрос соответствует примеру в кабинете: name/from/to/subject/html и дополнительная текстовая версия text. Нормальная проверка TLS включена. Автоматического повтора или переключения на другого отправщика после неопределённого ответа нет.

## Действия в кабинете

1. Дождаться одобрения домена episyhub.space после модерации, включить для него «Транзакции».
2. Выключить «Трекинг» домена: он не нужен для одноразовых ссылок, перезапись ссылки нежелательна. Не добавлять неизвестные параметры трекинга в API: управление здесь производится в кабинете.
3. Получить API-ключ в «Мой профиль» / API, как указано в документации. Это не SMTP-пароль. Не публиковать ключ или SMTP-пароль в чате, GitHub и NEXT_PUBLIC-переменных.
4. Уточнить у поддержки доступ к транзакционной отправке на адреса новых пользователей на текущем бесплатном тарифе. Квота не равна разрешению на отправку до одобрения домена/аккаунта. По скриншоту кабинета лимит аккаунта — 100 писем в час; отдельные суточные и месячные ограничения задаёт сервис.

## Vercel

В Settings → Environment Variables для Production добавить:

| Name | Value |
| --- | --- |
| EMAIL_PROVIDER | smtpbz |
| SMTPBZ_API_KEY | API-ключ SMTP.bz, Sensitive |

Существующие EMAIL_FROM=noreply@episyhub.space, EMAIL_FROM_NAME=EpisyHub, APP_URL=https://episyhub.space оставить. Старый UNISENDER_GO_API_KEY можно временно сохранить для ручного отката; он не используется при EMAIL_PROVIDER=smtpbz. Значение EMAIL_PROVIDER по умолчанию — unisender, поэтому одно объединение PR не меняет отправщика без настройки переменной.

Настроить переменные до объединения PR, затем объединить его в main и дождаться Ready / Production. Для Preview аналогично указать ключ и провайдера, а APP_URL должен указывать на нужную Preview, чтобы подтверждение оставалось в тестовой выкладке. После изменения переменных существующую сборку нужно пересобрать.

Новых SQL-миграций нет. Сохранённые заявки, пароли, пользователи, библиотека и попкорн не изменяются при смене отправщика.

## Проверка

Сначала попробовать повторную отправку для сохранённой заявки. Проверить входящее письмо и папку «Спам», открыть ссылку, нажать «Подтвердить почту», затем войти. Повторное открытие ссылки не должно выдавать повторную награду. После успешной проверки проверить доставку на доступные пользователю адреса разных почтовых сервисов.

Если MAIL-SMTPBZ-HTTP-401 — проверить, что взят именно API-ключ, и после его сохранения пересобрана Production. При HTTP 403 проверить модерацию, разрешение транзакций, доступ и квоту в кабинете. При HTTP 400 проверить отправителя и ошибку в журнале сервиса. MAIL-NETWORK — соединение/таймаут. Сырые ответы SMTP.bz, адреса получателей, ключи и токены не выводятся в логи или браузер.

DNS Unisender не удалять до проверки доставки SMTP.bz. Пока работают оба отправщика, SPF остаётся единственной записью с обоими include. После полного перехода очистить устаревшие записи отдельным изменением.

## Автоматические проверки

Тесты используют локальный почтовый сервер, проверяющий raw Authorization и структуру SMTP.bz, и отдельную схему локальной PostgreSQL. Настоящие письма и платные вызовы не отправляются. Проверяются создание аккаунта только после подтверждения, одноразовость, повторная отправка, истечение срока, восстановление после отказа и безопасная диагностика. В production-подключении разрешён только HTTPS на документированный адрес API; локальное HTTP-переопределение возможно только вне production для тестов.

# Единые правила прогресса

Исправления охватывают ручные отметки серии/сезона, быструю отметку и отмену, смену статуса, библиотеку, профиль, достижения, рейтинг пользователей и ленту друзей. Миграция и новые переменные окружения не нужны.

## Правила

| Действие | Результат |
| --- | --- |
| Отметить серию | Увеличить прогресс; записать дату только при переходе из непросмотренной в просмотренную; удалить таймкод |
| Повторить отметку | Сохранить прежнюю дату, включая неизвестную дату старой отметки |
| Отметить сезон | Сохранить все его серии одной транзакцией; завершить тайтл, только если просмотрен весь известный каталог и он покрывает объявленное количество серий |
| Снять отметку | Удалить дату этой отметки; из «Просмотрено» перейти в «Смотрю»; другие статусы сохранить |
| Выбрать «Просмотрено» | Отметить все известные серии и синхронизировать флаг завершения; для фильма при необходимости создать одну каноническую часть |
| Выбрать «Просмотрено» при неполном каталоге сериала | Отказать с 409 и предложить открыть трекер; статус, оценки и прогресс не менять частично |
| Выбрать «Смотрю», «В планах» или «Брошено» | Сохранить существующие отметки, даты и таймкоды; сброс прогресса не подразумевается |
| Отметить первую серию из планов | Перейти в «Смотрю» либо «Просмотрено», если уже просмотрен весь каталог |
| Сохранить только время | Сохранить статус; время допускается только у непросмотренной серии. Можно явно снять отметку и одновременно сохранить время |
| Изменить оценку, избранное или заметку | Сохранить текущий статус; не сбрасывать прогресс |
| Повторно добавить существующий тайтл через wishlist | Сохранить текущий статус и отметки |

Тайтл с явным статусом «Смотрю» может сохранять 100% отметок: это осознанный переход пользователя без скрытого сброса. Новый интерфейс полного пересмотра и журнал повторных просмотров в этот этап не входят.

«Просмотрено» описывает доступный каталог, а не обещание, что у сериала никогда не появятся новые сезоны. Отдельные правила подписки на продолжения будут частью календаря.

## Согласованность и параллельные запросы

`src/lib/library-mutations.ts` объединяет старые API записи. Сохраняются их адреса: `/api/user-shows` и `/api/user-shows/[id]` используют Show.id; `quick-progress` и старый маршрут `episodes/[epId]` используют UserShow.id (а epId — EpisodeProgress.id).

Запись пользователя блокируется в сериализуемой транзакции. Отметки, даты и статус сохраняются вместе; при конфликте возвращается 409. Ревизия записи монотонно увеличивается, поэтому старая отмена не может затереть ручные изменения. Пакетные операции не выполняют отдельный запрос сохранения для каждой серии; проверен сезон из 500 серий.

Быстрая отметка фильма без строки Episode теперь создаёт каноническую часть и датированный личный прогресс. Отмена удаляет только созданный личный прогресс и восстанавливает статус; часть общего каталога остаётся. Остальные ограничения подписанной отмены прежние: 10 минут, текущая страница, проверка владельца и последующих изменений.

GET трекера может заполнить неполный, а не только пустой каталог из TMDB. Запросы к TMDB остаются вне транзакции прогресса. Если источник недоступен, недостающие серии не придумываются.

## Статистика и старые данные

`src/lib/progress.ts` задаёт общий подсчёт: серии другого тайтла не учитываются, фильм считается одним фильмом, а не серией для достижений. Источник типа — общий Show, источник завершения — status, а не устаревший отдельный флаг. Просмотренные серии брошенных тайтлов продолжают учитываться как состоявшиеся просмотры. Оценки отдельных эпизодов не подменяют оценку всего тайтла.

Время просмотра остаётся приблизительным: количество отмеченных серий умножается на длительность из каталога (при её отсутствии сохранены прежние оценки длительности: 45 минут для серии и 110 для фильма). Убраны вымышленные десять серий и предположение, что завершённый статус всегда означает наличие всех отметок. Поэтому старое завышенное число часов может уменьшиться. Уже завершённый фильм учитывается как один просмотр, даже если у старой записи ещё нет личного прогресса.

Автоматического массового исправления рабочей базы нет. Исторические даты без данных остаются неизвестными. Если старый статус уже противоречит отметкам из-за прежних ошибок, дата и потерянное намерение пользователя не восстанавливаются догадкой. Такой тайтл можно явно исправить в трекере; массовый ремонт требует отдельного отчёта и резервной копии.

## Проверки и выкладка

- 38 API/security-тестов с настоящими сессиями и временной схемой локальной PostgreSQL: права, валидация, атомарность, неполный каталог, даты, статусы, фильмы, 500 серий, параллельные операции, отмена и согласованность статистики.
- 43 браузерных теста: в том числе немедленное обновление всех отметок и счётчика при выборе «Просмотрено», возобновление после снятия отметки, сохранение отметок при смене статуса и предыдущие сценарии навигации/библиотеки/трекера.
- TypeScript, ESLint изменённых файлов и production-сборка `npm run build -- --webpack`. Turbopack ограничен служебными портами этой среды; команда проекта и настройки Vercel не менялись.
- Рабочая Supabase не использовалась в проверках. Проверки UI используют Chromium и подставные API, API-тесты — настоящий локальный PostgreSQL.

# Календарь новых серий и уведомления

## Интерфейс

- `/calendar`: неделя и месяц, переход между периодами, «Сегодня», выбор дня, фильтры «Смотрю», «В планах», «Завершённые», «Все». Выбранные день, вид и фильтр сохраняются в URL и работают с возвратом браузера.
- Список показывает сериал, сезон/серию, дату оригинального релиза, личную отметку и переход в трекер. Нет точных часов или обещания наличия перевода.
- Подписка доступна в строке выпуска, в списке сериалов календаря (включая сериалы без известной даты) и в трекере.
- Колокольчик в шапке: счётчик непрочитанных, настольная панель с «Новые»/«Все», «Прочитать все», переход к полной странице. На телефоне открывается `/notifications`.
- `/notifications`: новые/все, отдельная отметка прочитанного, чтение всех, следующая страница, настройки. «Новые серии» останавливает создание новых уведомлений, сохраняя историю. «Включать для новых сериалов» влияет только на последующие добавления, включая трекер и wishlist.
- На телефоне добавлен пятый пункт нижней навигации. На компьютере календарь заменил дублирующую ссылку на планы; сами планы доступны в библиотеке.

## Даты и источник

Даты хранятся в `Episode.airDate` как PostgreSQL DATE. Они отображаются как календарные даты без пересчёта полуночи в часовой пояс зрителя. Его часовой пояс нужен только для определения сегодняшнего дня и даты начала подписки.

Используются существующие серверные `TMDB_API_KEY`, `TMDB_READ_ACCESS_TOKEN` либо `NEXT_PUBLIC_TMDB_API_KEY`; новых ключей не требуется. Поле tmdbId должно быть связано с сериалом. Неизвестные даты не придумываются, специальные сезоны с номером 0 не загружаются. Если связи с источником нет, карточку можно открыть в трекере, где уже существует получение данных из TMDB.

Кеш расписания действует 6 часов для обновлённого диапазона; повторная попытка одного сериала ограничена минутой и разделяется всеми пользователями этого сериала. Один запрос обновляет не больше двух сериалов, для каждого — не больше шести пересекающихся сезонов. Слишком неопределённый ответ не объявляется полным. В календаре автоматически обновляются первые десять подходящих сериалов выбранного фильтра; большая библиотека продолжает обновление кнопкой. При ошибке сохранённые даты остаются доступны.

Синхронизация меняет только каталог: дату, название и недостающие строки Episode. Личный прогресс и его даты не переписываются. Запросы к TMDB выполняются вне транзакций PostgreSQL. Новый сезон сам по себе не меняет выбранный пользователем статус просмотра.

## Уведомления

Это уведомления внутри сайта, без email, browser push или фонового cron. Пока сайт открыт, колокольчик обновляется примерно раз в минуту; возвращение во вкладку и действия с подписками также запускают проверку. За одну проверку колокольчика обновляется расписание одного подходящего подписанного сериала; календарь обновляет его пакетно быстрее.

Для каждой подписки сохраняется день включения. Создаются уведомления о непросмотренных выпусках с датой не позже сегодняшней, не раньше дня подписки и не старше 30 дней. Фильмы и брошенные сериалы не порождают новые уведомления. Это ограничение относится к созданию записей, а не к сроку хранения уже созданной истории.

Уникальный ключ `(userShowId, episodeId)` не даёт создать повтор одного выпуска. Прочтение и глобальное отключение не удаляют историю. Если источник перенёс релиз в будущее или убрал дату, запись временно исключается из выдачи и счётчика; при возвращении даты сохраняется её прежнее состояние прочтения. Удаление тайтла из личной библиотеки удаляет связанные с ним уведомления.

Чтение всех ограничено последним ID из показанного снимка списка: новые записи, появившиеся во время запроса, не помечаются прочитанными. Все API проверяют текущий аккаунт, изменения проверяют Origin, ответы не кешируются общим HTTP-кешем. У новой таблицы включён RLS без публичных политик: доступ предполагается через серверную роль Prisma, которая владеет таблицей или имеет BYPASSRLS. Подписка не изменяет ревизию прогресса и не ломает его быструю отмену.

## Выкладка в Supabase и Vercel

Этап требует **добавочной миграции до выкладки кода**. Рабочая база в процессе разработки не изменялась. Новая версия Prisma запрашивает добавленные поля, поэтому немигрированная preview-база тоже должна быть обновлена до проверки входа.

1. Сохранить актуальную резервную копию базы. Например, из безопасно настроенного окружения с прямым или session-pooler подключением: `pg_dump --dbname="$BACKUP_DATABASE_URL" --format=custom --file=my-shows-before-calendar.dump`. Для BACKUP_DATABASE_URL нужна libpq-совместимая строка без параметров Prisma вроде schema/pgbouncer. Не использовать transaction pooler для дампа и не публиковать строку подключения.
2. В **SQL Editor рабочего проекта Supabase**, соответствующего Production DATABASE_URL в Vercel, выполнить файл целиком: `prisma/migrations/20261026000000_release_calendar/migration.sql`. Он содержит BEGIN/COMMIT, добавляет поля/таблицу/индексы, включает RLS и не удаляет аккаунты или прогресс. Не выполнять отдельные фрагменты повторно, если миграция уже применена.
3. Проверить результат запросом ниже. Старый deployment может продолжать работать с добавленными полями; для его отката удалять их не нужно.
4. Если SQL применён вручную, после успешной проверки отметить эту миграцию как выполненную через Prisma CLI **с безопасно настроенным подключением к той же базе**: `npx prisma migrate resolve --applied 20261026000000_release_calendar`. CLI не читает `.env.local` автоматически. Не запускать `db push` в рабочей базе; не запускать все исторические миграции без проверки `_prisma_migrations`, поскольку база переносилась вручную.
5. Проверить Vercel Preview: вход, календарь недели/месяца, подписку, прочтение, настройки, трекер и сохранность прогресса. Если preview был собран до миграции, при необходимости повторить deployment.
6. Ready for review → Merge pull request. После Ready в Vercel повторить проверки на основном домене.

## Проверки

- 47 API/security-тестов с реальными сессиями и временной схемой локального PostgreSQL. Добавочная миграция применена к заполненной старой схеме, проверены сохранность прогресса и RLS.
- 57 браузерных сценариев в Chromium: календарь недели/месяца на ширинах 320/390/1440, возврат и перезагрузка, подписки, ошибки, уведомления, настройки, гость, клавиатура и прежние функции. Отдельно проверен зритель в Лос-Анджелесе на границе календарного дня.
- TypeScript, ESLint изменённых файлов и production-сборка `npm run build -- --webpack`. Turbopack ограничен служебными портами этой среды; команда сборки проекта и Vercel не менялись.
- Ответы TMDB в тестах подставлены; настоящий ключ, рабочая Supabase, YouTube и Safari не использовались. Реальное получение дат следует проверить в Vercel Preview после применения миграции.

Локальная база разработки этой среды также обновлена этим SQL. Перед применением скрипт проверил, что адрес — localhost/127.0.0.1; количество аккаунтов и записей прогресса до и после совпало. Это не применение миграции к Supabase.

# Первый этап исправлений безопасности

Устранены подстановка аккаунта для гостя, выдача хеша пароля, изменение чужого прогресса, подтверждение отправителем своей заявки и сохранение произвольного файла как баннера. Банк и ответы игры «Больше или меньше» теперь хранятся на сервере; повторное или параллельное списание одного раунда отклоняется атомарной проверкой состояния в PostgreSQL.

Также исправлены адрес API счётчиков, обработка недоступной коллекции, потеря Bearer-заголовка TMDB, проверка диапазона оценок и статусов в основных API библиотеки, сброс флага завершения при изменении статуса. Чтение профиля больше не изменяет библиотеку.

Удаление тайтла из планов теперь использует отдельный DELETE, ограниченный владельцем и статусом planned. Оно удаляет запись библиотеки с её зависимыми личными оценками/прогрессом; общий каталог и библиотеки других пользователей сохраняются. Старый запрос со status=null больше не принимается и не переводит тайтл в «смотрю».

Проверено в рабочей среде: 16 регрессионных тестов прошли; production-сборка и TypeScript прошли; проверка ESLint новых модулей, переписанной игры и обработчиков безопасности прошла. Общий линтер пока сообщает 106 ошибок и 10 предупреждений из оставшегося кода. Chromium на production-сборке подтвердил вход, отображение счётчика, обработку отсутствующей коллекции и недоступного TMDB, серверную проверку ответа, восстановление банка после перезагрузки, выдачу награды и запрет повторной выплаты. Проверка игры использовала временный раунд в локальной базе; настоящая интеграция TMDB не проверена. Временные пользователи, тайтлы, файлы и тестовые схемы удалены.

## Установка и выкладка

1. Установить зависимости через `npm ci`. Для безопасного перекодирования баннеров добавлен прямой dependency `sharp` уже используемой проектом версии.
2. Применить миграцию `20261022000000_secure_higher_lower_state` к базе приложения до запуска новой версии. Она добавляет только nullable JSONB-поле `User.higherLowerState`, не меняя балансы и попытки. Для базы с корректной историей Prisma используется `npx prisma migrate deploy`; сначала проверить `npx prisma migrate status`. Если база ранее создавалась через `db push`, согласовать историю миграций отдельно — не применять reset к рабочей базе.
3. Выполнить `npx prisma generate` и `npm run build`, затем перезапустить приложение. Клиент игры и API должны обновляться вместе.
4. На опубликованной версии проверить вход, свою библиотеку, отказ гостю, трекер серий, баннер и награды. В этой задаче публичный сервер не изменялся.

Для Prisma CLI нужен `DATABASE_URL` в окружении: `.env.local` автоматически читает Next.js, но не Prisma CLI.

### Vercel + Neon: применение только этого изменения через SQL Editor

1. В Vercel откройте настройки проекта и найдите переменную `DATABASE_URL` для **Production**. Значение не публикуйте и не отправляйте в чат. В Neon выберите соответствующие ей проект, ветку и базу. Не путайте их с локальной или preview-базой.
2. Перед изменением создайте доступную в вашем тарифе резервную копию/ветку Neon. В **SQL Editor** выбранной рабочей базы выполните:

   ```sql
   ALTER TABLE public."User"
     ADD COLUMN IF NOT EXISTS "higherLowerState" JSONB;
   ```

   Это добавляет только поле состояния игры, не выполняет старые миграции и не удаляет данные. Затем проверьте результат:

   ```sql
   SELECT column_name, data_type
   FROM information_schema.columns
   WHERE table_schema = 'public'
     AND table_name = 'User'
     AND column_name = 'higherLowerState';
   ```

   Ожидается одна строка с типом `jsonb`. Если таблица не найдена, сначала проверьте выбор базы и схему — не создавайте новую таблицу User вместо существующей.
3. SQL Editor не обновляет историю Prisma. После успешной проверки выше в терминале с этой версией репозитория и **безопасно настроенным прямым подключением к той же рабочей базе через DATABASE_URL** отметьте именно эту миграцию как выполненную:

   ```bash
   npx prisma migrate resolve --applied 20261022000000_secure_higher_lower_state
   npx prisma migrate status
   ```

   `resolve` здесь только записывает факт уже выполненного SQL; он не заменяет SQL и не запускает остальные миграции. Если миграция уже помечена применённой, повторять resolve не нужно. Старые ожидающие миграции требуют отдельной проверки истории; не запускайте их вслепую через deploy/reset/db push.
4. После добавления поля объедините ветку исправлений в производственную ветку GitHub (обычно `main`). Если Vercel подключён к ней, это запустит production-деплой. Дождитесь успешной сборки и проверьте вход и библиотеку. Для мини-игры нужен действительный серверный ключ TMDB в Vercel. Одно сохранение изменений в облачной среде Codex не обновляет Vercel.

При обычной согласованной истории Prisma вместо ручного SQL и resolve используется стандартный `migrate deploy`; не нужно выполнять оба варианта подряд.

Старые игровые раунды без серверного состояния начинают заново. Уже начисленные балансы сохраняются. Ошибочные прошлые начисления автоматически не пересчитываются.

Ранее загруженные HTML/SVG-файлы это изменение не удаляет. Перед публикацией нужно проверить существующее хранилище и убрать либо изолировать активные документы. Новые локальные баннеры сохраняются только как перекодированный WebP; допустимы исходные JPEG/PNG/WebP до 10 МБ и 40 млн пикселей. Постоянное хранение в `public/uploads` по-прежнему требует сохраняемого диска; для serverless нужен отдельный объектный storage.

Если уязвимая версия уже была публичной, отдельно оценить доступность профилей и экспорта, журналы обращений и необходимость сброса паролей. Отчёт об аудите не доказывает, что утечка происходила.

## Регрессионные проверки

`npm run test:security` запускает настоящий Next.js и проверяет HTTP API с двумя Credentials-сессиями, гостем и PostgreSQL. Нужна локальная PostgreSQL и установленный Prisma Client. Берётся `TEST_DATABASE_URL` или `DATABASE_URL` из `.env.local`. Внешние адреса БД запрещены тестовым раннером.

Тесты создают отдельную схему `test_security_<pid>_<timestamp>`, применяют схему и новую SQL-миграцию, после выполнения останавливают свой сервер, удаляют тестовые файлы и схему. Схема приложения не очищается. Не запускайте одновременно с другим `next dev` в этом checkout: Next.js использует общий dev-lock. Порт тестов по умолчанию 3317, можно изменить через `SECURITY_TEST_PORT`.

Проверяются права гостей и удалённых аккаунтов, безопасная выдача профиля, изоляция прогресса, согласие на дружбу, отбрасывание HTML/SVG и поддельного MIME, перекодирование настоящего изображения, валидация библиотеки, скрытые ответы и восстановление раунда, повторы и параллельные выплаты, предел 15 единиц за пять раундов, неудачные и просроченные раунды. Загрузка TMDB проверяется отдельно с явно подставленным ответом; действительный ключ не используется и полноценная внешняя интеграция этим не подтверждается.

## Следующие задачи

Этот этап не исправляет все пункты аудита. Остаются защита от перебора и ограничения частоты запросов, атомарность ежедневных наград и викторины, завершение перехода Title → Show, неоднозначность внутренних и TMDB ID, побочные эффекты GET трекера, мобильная навигация и поиск, постоянное файловое хранилище, часть старых ошибок линтера и обновление зависимостей. Не применять `npm audit fix --force` без проверки совместимости.
